# LWJGL2 surface used by b1.7.3

Every `org.lwjgl` class, method and field that b1.7.3's client classes reference, from a constant-pool scan of the
Feather-mapped jar (2026-11-12). This includes the paulscode sound classes shipped inside the game jar
(`LibraryLWJGLOpenAL`, `ChannelLWJGLOpenAL`, `SourceLWJGLOpenAL`). No direct jinput references: controllers go through
`org.lwjgl.input.Controllers`. 17 classes, 161 distinct references.

"Same in LWJGL 3" means LWJGL 3.4.3 has a static method with this exact name and descriptor, so a game call site links
to it unchanged. Every other row needs the compatibility layer (0.4). Checked by script against the LWJGL 3.4.3 `lwjgl`,
`lwjgl-opengl` and `lwjgl-openal` jars, public members only: 84 references resolve, 15 members are missing from
classes LWJGL 3 has (the 12 GL/AL10 signatures below plus `AL.create`, `AL.isCreated` and the non-public
`AL.destroy`), and 11 classes are absent.

## What this means for the layer (input to 0.4's precedence work)

- LWJGL2 and LWJGL 3 **share class names** in `org.lwjgl.opengl` (`GL11`, `ARBOcclusionQuery`, `ARBVertexBufferObject`),
  `org.lwjgl.openal` (`AL`, `AL10`) and `org.lwjgl` (`BufferUtils`). Whichever `org.lwjgl.opengl.GL11` the class loader finds
  first is the only one. So the profile's LWJGL2 jars must lose, or not be loadable at all (0.4's precedence step), and
  the LWJGL2-only signatures above must exist on the classes that win.
- Two ways to supply those signatures, to decide in 0.4:
  1. **Merged classes:** at build time, add the LWJGL2-only overloads (and the `ContextCapabilities`-style fields) to
     copies of LWJGL 3's `GL11`, `ARBOcclusionQuery` and `AL10`, as static bridges.
  2. **Call-site rewrite:** a transformer over Minecraft's classes (and paulscode's) that points each LWJGL2-only member
     reference at our own bridge class. LWJGL 3's classes stay untouched, and the LWJGL2-only classes (`Display`,
     `Keyboard`, `Mouse`, `GLContext`, …) can live in our own package instead of `org.lwjgl`.
  The rewrite keeps LWJGL 3's jars byte-identical (licence-clean, easy to update). The merge needs no transformer, but
  it ships modified LWJGL classes. Either way the profile's LWJGL2 must not shadow LWJGL 3.
- Natives can't be relocated: LWJGL 3's JNI symbols are bound to the `org.lwjgl.*` names, so LWJGL 3 stays in
  `org.lwjgl`.
